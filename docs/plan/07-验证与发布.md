# 验证与发布

## 1. 分层验证

纯逻辑测试验证解析、EditPlan、行列映射、锚定和导出。DOM 集成测试验证 token 拆分、重复渲染与事件清理。真实宿主验证输入法、选区、撤销、视图切换、窗口和设备操作。

建立专门测试 Vault，使用合成与公开许可样例；开发插件复制到测试 Vault 的实际 configDir/plugins 目录。自动构建与人工截图共同记录版本、设备、操作及结果。

## 2. 必测样例

| 范围 | 样例 | 预期 |
| --- | --- | --- |
| 正文 | 默认/六色、相邻片段、空白边界 | 保留颜色身份和原文 |
| 正文结构 | 粗体、链接、脚注、表格、列表、callout | 原结构和链接可用 |
| 编辑 | 部分改色、跨片段、跨段、多光标 | 精确变更，一次撤销 |
| 行内代码 | 反引号、`==`、HTML 字面值 | 识别为代码内容 |
| 围栏 | 反引号/波浪线、不同长度、嵌套示例 | 对应正确代码块 |
| 容器 | 引用、列表、callout 内代码块 | 逻辑列与源偏移一致 |
| 代码字符 | Tab、中文、emoji、CRLF、空行、末尾换行 | 定位和复制准确 |
| 代码显示 | 软换行、长行、跨行字符串/注释 | 行背景与文本重点正确 |
| 代码编辑 | 标行、标词、交叠、多个 segment | 保留代码及各条标注身份 |
| 锚定 | 插入前置行、重复函数、复制块、块移动 | 命中正确目标或展示待定位状态 |
| 语法着色 | C、C++、Python、JS/TS、JSON、Bash、ASM | 重点层与 token 共存 |
| 扩展围栏 | mermaid、dataview、tasks | 与专用处理器分工明确 |
| 生命周期 | 启停、重启、窗口关闭、布局恢复 | 资源清理及视图状态正确 |
| 索引 | 创建、修改、删除、文件与目录改名 | 查询结果与最新内容一致 |
| 同步 | 外部修改、重复 ID、合并冲突样例 | 按当前文件解析并显示对应状态 |
| 导入 | mark/style/class、Hilo、常见 fence 参数 | 预览与变更对应，可恢复 |
| 导出 | 原代码、摘录、HTML/PDF、目标 fence 格式 | 内容、链接与支持的样式保留 |

## 3. 性质与回归测试

- 应用后移除正文高亮可还原内容，含原有强调语法。
- 应用/移除代码标注前后，提取出的代码内容逐字符相等。
- 重复应用同一语义满足幂等性。
- 解析→序列化→解析保留版本、ID、语义及范围信息。
- 编辑后选区映射覆盖实际逻辑文本。
- 同一 Markdown 的索引模型与宿主可见对象匹配。
- 迁移执行后再执行无额外变化，逐文件恢复匹配原始文本。

随机生成的围栏长度、字符串、转义和 UTF-16 字符串用于边界测试。固定失败输入进入 fixtures。快照验证采用实际行为断言，布局截图只作为视觉回归的一部分。

## 4. 性能目标及测量

下列数值为工程目标，尚待测量。记录 Obsidian、系统、硬件、插件版本，区分冷启动与热缓存，结果采用多次运行的 p50/p95。

| 场景 | 初始目标 | 方法 |
| --- | --- | --- |
| 200 KB 活动笔记标注操作 | 插件处理 p95 ≤ 50 ms | performance 标记测纯处理与提交 |
| 文档编辑到当前侧栏更新 | p95 ≤ 200 ms | 事件起点到列表渲染完成 |
| 500 个代码行的重点更新 | p95 ≤ 50 ms | 区分解析、装饰及布局 |
| 1 万篇合计约 100 MB 笔记冷索引 | 展示进度，可随时操作当前笔记 | 分批队列与主线程长任务记录 |
| 大文件 | 验证 1 MB 文档、5000 行代码块 | 可见区装饰、分段处理与跳转 |
| 全库缓存 | 优先验证增量和重建一致 | 记录耗时、条目数与内存增量 |

移动设备独立记录同组样例，不套用桌面耗时。长任务检查以 50 ms 为观察阈值；缓存队列、渲染批次、第三方重渲染和事件合并分别计量。

## 5. 兼容矩阵

核心矩阵：最低支持版与当前稳定版 × 桌面编辑/Live Preview/阅读 × 深浅主题。平台覆盖 Windows、macOS、Linux、Android、iOS。扩展矩阵采用代表组合：Minimal、AnuPpuccin、Style Settings、Shiki Highlighter、Code Styler、Codeblock Customizer、多窗口与移动工具栏。

每个矩阵单元记录通过、问题及关联样例。平台验证分别保存真实设备证据；某平台尚未执行时明确标记“待验证”。`isDesktopOnly: false` 在 Android/iOS 核心流程通过后用于公开版声明。

## 6. CI 与仓库约定

实施阶段增加 GitHub Actions：依赖安装 → lint → typecheck → 单元/性质测试 → build → manifest 与产物检查。构建使用锁文件，CodeMirror/Obsidian external 与官方示例一致。

按功能建立分支，提交包含实现和对应验证说明；决策变更同步更新本目录。测试 Vault、用户笔记、运行缓存和本地配置保留在 Git 跟踪范围外。LICENSE 在工程基础阶段确定为 MIT，并建立第三方许可清单；引用或复用代码记录原始许可与文件来源。

本次交付为调研计划，仓库先提交文档；插件 CI、manifest 和 Release 在相应实施阶段建立。

## 7. 发布流程

依据[官方提交文档](https://docs.obsidian.md/Plugins/Releasing/Submit%20your%20plugin)，当前上架流程使用 Obsidian Community 目录：登录、关联 GitHub、提交插件，再处理自动审核反馈。历史资料中的 community-plugins.json PR 流程应结合届时官方说明核对。

发布时：

1. 检查插件 ID `highlight-boost` 在目录中唯一，名称、描述和最低版本与实际功能对应。
2. 完成 README、LICENSE、截图及安装说明，说明本地功能和使用方式。
3. 将 manifest 版本更新为 `x.y.z`，同步 `versions.json` 中所需的兼容映射。
4. 创建同名 tag；上传 `main.js`、`manifest.json`、`styles.css` 为 Release 附件。
5. 从 Release 全新安装，验证正文和代码的核心流程。
6. 使用 Obsidian Community 目录提交，按审核结果修订并发布新版本。

GitHub 公开仓库、GitHub Release、社区上架分别记录状态和链接。预览版可以通过手动安装或 BRAT 分发。

官方[开发者政策](https://docs.obsidian.md/community-directory/developer-policies)要求说明网络、账号和收费等功能，并遵循源代码许可。本项目首版采用设备本地处理；后续外部服务由独立功能方案描述数据流。用户输入的 UI 内容通过 DOM API 与宿主 MarkdownRenderer 构建，样式使用插件 class 和 CSS 变量。
